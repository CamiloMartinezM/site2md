# site2md 0.6.0

Version 0.6.0 makes `build` faster and changes nothing it produces. It adds no option. For the same input, the Markdown, the messages and the exit status are byte-identical to 0.5.0's, and so is the extraction result apart from the version it names.

On the benchmark page, one `build --extract … --entry-points-only --values-only --no-progress` step takes about 354 ms with the package and 267 ms with the executable on Windows, against 626 ms and 508 ms for 0.5.0 in the same run. Without `--extract`, the same build takes 232 ms and 176 ms, against 493 ms and 397 ms. Each saving below was measured on its own on that page with the package, so they overlap a little ([#84](https://github.com/CamiloMartinezM/site2md/pull/84)).

- **One parse per page.** 0.5.0 parsed a page, wrote the cleaned tree back to HTML, and parsed that again for the Markdown. 0.6.0 renders the Markdown from the first tree, which saves about 64 ms.
  - To keep the Markdown the same, the converter joins the text nodes that a removed element, or an end tag without a start tag, leaves side by side. The second parse used to merge them.
  - A page that would read differently the second time still takes the old route: one with a doctype or a declaration inside its content, with text inside an `<iframe>` or another raw-text element, or with a void element that Beautiful Soup before 4.15 left open. Of 70 saved public pages, 91 % take the single parse with Beautiful Soup 4.15, and 79 % with 4.12.
- **A cheaper pass over the page.** The converter finds the elements it removes, the links and images it resolves and the `<base>` element in one walk over the tags instead of one walk for each, which saves about 12 ms. markdownify asks at every element whether it is inside a `<pre>`, and the converter's tags now answer by walking up their parents instead of through Beautiful Soup's general search, which saves about 13 ms.
- **No reading back.** A remote build hands the fetched page and the converted Markdown to the next step in memory, instead of reading back the files it has just written, and `build --extract` runs the Extractor on the bytes that it saved. That saves about 47 ms on Windows, where the first read of a new file is when Microsoft Defender scans it.
  - A build writes the same files with the same bytes as before, including the ones that `--keep-temp` keeps.
  - The price is memory. 0.5.0 copied the converted pages from the workspace files into the output. 0.6.0 keeps them in memory until it writes the output, so a follow or site build needs memory for about twice the size of its output file while it writes it.
- **cyclopts only when it is needed.** A `build` command line made of the input, `--name value` options and flags is read without loading cyclopts, which saves about 26 ms. Help, errors and every other form, such as `--name=value`, a short option or an option given twice, go through cyclopts as before, so the help pages, the error messages and the exit statuses are the same.
- **Rich only when it is needed.** Without a progress bar and without a terminal, `build` prints its messages without loading Rich, which saves about 37 ms. That is what `--no-progress` now does in a script or a pipe, on top of the 20 ms that it saved before.
  - A message that Rich would wrap, or change in any other way, still goes through Rich. So does every message when there is a terminal, a progress bar, `FORCE_COLOR` or `TTY_COMPATIBLE`.
- **Soup Sieve only when it is needed.** Beautiful Soup imports Soup Sieve at start-up, and only a CSS selector uses it. It now loads at the first selector, which is follow mode's `--follow-selector`, and every other build saves about 22 ms.
- **The extraction modules load while the build waits.** With `--extract`, a thread imports marko, jsonschema and the other extraction modules while the build fetches and converts the page, which saves about 9 ms. A build that fails before it extracts exits without waiting for the thread.
- **A quieter garbage collector.** A run builds a few large trees and exits, so every command now collects garbage after 100,000 allocations instead of Python's default of 700 or 2,000, and skips the collector's last pass at exit. That saves about 12 ms and 10 ms.
  - A parsed page that is no longer needed stays in memory a little longer. Peak memory still fell, from 56 MiB to 45 MiB on the benchmark page, because there is one tree instead of two, and neither cyclopts nor Rich.
  - Python no longer finalizes objects that are still in a reference cycle when the command ends. site2md closes its own files, so this reaches only an Extractor provider that relies on such a finalizer, which Python never guaranteed to run.
- **An HTTPS handler only for HTTPS.** Since Python 3.12, urllib loads the system certificates when it creates an HTTPS handler, and it created one for every request, even for an HTTP page. site2md now creates the handler at the first HTTPS request and keeps it for the run, which saves about 8 ms per request.
- **Faster checks in extraction.** Extraction works out where each source section starts and ends once per document, instead of once for every source span of every record, and it normalizes the Markdown a run of characters at a time. That saves about 8 ms for the benchmark's 250 records.
- **The executable no longer bundles `multiprocessing`.** Nothing in site2md starts processes, and with the module present the executable imported it at every start, which took about 7 ms. An Extractor provider that needs `multiprocessing`, or `concurrent.futures.ProcessPoolExecutor`, uses the package, as for the other [limits of the executable](extractor-providers.md#using-a-provider-with-the-executable). `ThreadPoolExecutor` still works.
- **How the output was checked.** 0.5.0's converter and the new one agree on 27,042 conversions of 9,014 documents, on Python 3.12 and 3.14. Of 36,173 `build` command lines, the new binding handles 2,665, and cyclopts binds every one of those to the same values. The benchmark page, the benchmark's crawl and two live HTTPS pages give the same bytes.
  - On Python 3.10 with Beautiful Soup 4.12.0, one page that is nested too deeply to convert in either version fails with a differently worded `RecursionError`.
- **For contributors.** [ADR 0005](adr/0005-take-a-fast-path-only-where-the-output-is-the-same.md) records the rule behind the fast paths: a shortcut is taken only where its result is exactly what the full path gives. `pyproject.toml` now makes uv rebuild site2md when a source file changes, so `uv run --with .` no longer builds the executable from stale sources. The [speed research](speed-research-0.6.0.md) has the method, every measurement, and the experiments that were measured and left out.

The [0.4.0 release notes](release-0.4.0.md) still describe the remote modes and their limits. Publishing to PyPI or another package registry remains a separate maintainer action.
