# Read script-built pages from an installed browser, only when asked

From 0.7.0, `build --browser` reads a page in page mode from an installed Chromium-based browser instead of fetching it with `urllib`, so that content that a script adds is there. site2md starts the browser named in `SITE2MD_BROWSER`, or else Chrome, Edge or Chromium where each system installs them, headless and with a temporary profile. It speaks the DevTools protocol to it over `--remote-debugging-pipe` with a client of its own in the standard library, reads the page after 10 seconds of the page's own time (`Emulation.setVirtualTimePolicy`, which fast-forwards the page's timers and holds its clock still while a request is under way), and returns the same `RemotePage` that a fetch returns, so conversion, the workspace, `--keep-temp` and `--extract` don't change. A plain fetch's rules apply to the page's own document and give the same lines: only a final `2xx` response of type `text/html` or `application/xhtml+xml` is converted, with the type taken from the `Content-Type` header and not from what the browser guesses; redirects are followed; an HTTPS-to-HTTP move of the page, by a redirect, a script or a meta refresh, is refused through `Fetch` interception, before the http request leaves, and the browser starts with `HttpsUpgrades` and `HttpsFirstBalancedModeAutoEnable` off so that Chrome's own HTTPS upgrade and fallback can't make the page be requested elsewhere or look like a downgrade; the 30-second timeout runs from starting the browser to reading the page; `--max-page-size-mib` limits the page as the browser shows it; and the address that the browser ends on is the source. The browser loads whatever the page asks for, from any host, and nothing is blocked or checked against `robots.txt`, because the entry page is a direct user request and these requests belong to it. The User-Agent is the browser's own followed by ` site2md/<version>`, set on every target that the page opens, such as a frame of another site. site2md doesn't hide the automation or answer a browser check, the browser keeps its sandbox (site2md never passes `--no-sandbox`), downloads are refused, dialogs are dismissed, and the temporary profile, the temporary files that the browser makes (its `TMPDIR`, `TMP` and `TEMP` point into the folder of the profile) and every browser process are gone after a success, a failure and an interruption, with `--keep-temp` too, and a folder that can't be removed fails the build. Only `--browser` loads the module, so a build without it makes the same requests, writes the same bytes and loads nothing new (ADR 0005).

`--browser-profile FOLDER` swaps the temporary profile for a folder that stays, so that a page that only signed-in visitors get can be read with a session. site2md has no window of its own for signing in: the person starts the same browser with `--user-data-dir=FOLDER`, signs in and closes it, and only what the browser keeps after it closes is in the folder. The folder has to exist, so that a typo can't start a profile that reads the page as a stranger. Only the build's own temporary folder, which holds the browser's log, is ever removed, so the person's folder is never removed, emptied or copied from, `--keep-temp` included. A folder that another browser has open makes a second browser stop at once, and the build says that another browser may have it open. Chrome refuses remote debugging on its everyday profile, so the folder can't be that one. The session is an account's, so the option is for sites whose terms allow automated access.

The price is that a tool that says it needs no browser can now drive one, that there are two ways to fetch a page, and that a build asks for far more than one request, to hosts that the person didn't name. Part of the protocol, `Emulation.setVirtualTimePolicy`, is marked experimental, though Chrome's own `--virtual-time-budget` relies on it. How a browser gets its pipe differs by platform (two inherited handles named in `--remote-debugging-io-pipes` on Windows, file descriptors 3 and 4 from `os.posix_spawn` elsewhere), and a build depends on the installed browser's version and on whether it can start its sandbox. Tests through the installed command hold it together: `tests/test_browser_build.py` builds pages whose scripts make the content against the local server, over a real TLS server for the downgrade, and checks that no browser process and no folder of the run is left; the browser tests run, and aren't skipped, in the Windows and Ubuntu jobs; the executable's smoke test builds one page with `--browser`, because a module missing from the frozen build shows only at run time; and the start-up tests record that a plain build never loads the browser module.

The alternatives were another way to run a browser, another way to talk to it, another rule for when the page is ready, or a filter on what it loads. Playwright as an optional extra adds 118 MB to an install of 11.5 MB and can't reach the executable. The browser's own `--dump-dom` exits 0 whatever happened, so it prints a 404's body, the JSON viewer, the page that a redirect led to and nothing for a refused connection, and it can't keep the README's promise of final, nonempty `2xx` HTML. `--remote-debugging-port` needs a WebSocket client and opens a loopback port with no password that any process on the machine can use. The `networkIdle` event reads a page before a script has asked for its data, and a selector is exact but slower, and the page runs in real time, so it isn't the default and is the option `--wait-for` instead ([#98](https://github.com/CamiloMartinezM/site2md/issues/98)): it reads the page as soon as an element matches, which is the way to read a page that keeps a request open, and it fails with one line that names the selector when none matches within the timeout. Blocking other hosts breaks pages, and blocking images, fonts and style sheets saves requests and no time and can change what a page shows; ADR 0005 allows a shortcut only where the result is the same, so that could only ever be an option that is off by default. Reading a site's own API takes code for each site and belongs in a provider, as ADR 0002 does for Extractors, so it is a proposal of its own. Firefox [removed its support for the protocol in version 141](https://fxdx.dev/cdp-retirement-in-firefox/) and Safari never had it. Each would change what a user gets or what a build costs, so none was taken ([#96](https://github.com/CamiloMartinezM/site2md/issues/96), [#97](https://github.com/CamiloMartinezM/site2md/issues/97)).
